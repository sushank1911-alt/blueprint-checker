ABSTRACT

The Examination Question Paper Blueprint Checker and Validation System is a specialized academic software tool engineered to automate, standardize, and verify the structural and cognitive composition of semester examination question papers. In autonomous institutions such as Rajeev Gandhi Memorial College of Engineering & Technology, question papers must strictly adhere to predefined institutional blueprints mandated by Outcome-Based Education (OBE) and the National Board of Accreditation (NBA). These blueprints define required distributions across course units (Unit 1 to Unit 5), Course Outcomes (CO1 to CO5), and Bloom's Revised Taxonomy levels (L1 Remember to L6 Create).

Traditionally, verification of blueprint compliance is performed manually by department scrutiny boards. Manual scrutiny requires considerable effort, is prone to arithmetic slips, lacks objective Bloom's assessment, and provides no systemic check against duplicate or highly similar questions. To eliminate these weaknesses, the proposed system provides an automated validation engine implemented in the C programming language.

The system is partitioned into five distinct modules:

  1. Module 1 (Blueprint Management): Captures, validates, and stores reference institutional standards including units, Course Outcomes, topics, expected questions, and marks.
  2. Module 2 (Question Paper Management): Maintains the actual question inventory with question statements, marks, units, CO mapping, and cognitive tags.
  3. Module 3 (Data Organization & Analysis): Aggregates multidimensional frequency matrices across units, Course Outcomes, and cognitive levels, and computes a Weighted Paper Difficulty Index.
  4. Module 4 (Blueprint Checking & Comparison Engine): Evaluates category-wise discrepancy equations, identifies over/under allocations, and derives a normalized Academic Compliance Percentage Score.
  5. Module 5 (Report Generation & File Management): Displays real-time ANSI color-coded evaluations on the console and exports official printable verification audit reports (audit_report.txt) and Microsoft Excel spreadsheets (audit_report.csv).

Furthermore, as an enhancement tailored for the CSE (AI & ML) curriculum, the application integrates an AI-based Action Verb Natural Language Classifier that automatically cross-checks question statements against Bloom’s Taxonomy levels, alongside a Jaccard Word Similarity Redundancy Detector to prevent duplicate examination questions. The resulting application ensures high academic rigor, supports fair and balanced student evaluations, and creates seamless digital audit trails for institutional accreditation.

1. INTRODUCTION

1.1 Project Overview

The Examination Question Paper Blueprint Checker is an academic auditing application developed in C to verify that semester examination question papers strictly conform to institutional assessment guidelines, Course Outcomes (COs), and Bloom's Revised Taxonomy levels.

1.2 Purpose

The purpose of the system is to provide an automated, mathematical scrutiny tool for academic scrutiny boards, course coordinators, and examination cell officers. It replaces manual scrutiny forms with an automated audit pipeline.

1.3 Objectives

  • Maintain an institutional blueprint specification across units, topics, Course Outcomes (CO1 to CO5), and cognitive levels (L1 to L6).
  • Inventory question papers and validate individual marks, unit distributions, and question counts.
  • Compute mathematical discrepancy equations across every unit and learning outcome.
  • Calculate an Academic Compliance Percentage Score and a Weighted Difficulty Index.
  • Incorporate NLP action-verb validation and Jaccard token similarity checks to eliminate duplicate questions.
  • Generate official, printable audit certificates (audit_report.txt) and spreadsheet files (audit_report.csv).

1.4 Scope

The scope covers autonomous B.Tech question paper structures (standard 70-mark theory papers distributed across 5 units and 5 Course Outcomes).

1.5 Intended Users

Department Scrutiny Committee members, Heads of Departments (HOD), Course Coordinators, and Institutional Examination Cell Auditors.

2. PROBLEM STATEMENT, OBJECTIVES, AND SCOPE

2.1 Problem Statement

Preparing balanced examination question papers requires adherence to institutional assessment guidelines that define the distribution of questions across various difficulty levels and learning outcomes. Manual verification of blueprint compliance may result in inconsistencies, calculation errors, delayed review cycles, and non-compliance with NBA Outcome-Based Education requirements. A structured examination blueprint validation system is required to analyze question paper composition, verify compliance with predefined assessment standards, evaluate mark distribution, and generate validation reports that support fair and standardized examinations.

2.2 Proposed Solution

An automated software application developed in ANSI C that accepts blueprint constraints, aggregates question parameters into multi-dimensional matrices, flags deviations, calculates compliance scores, and saves persistent verification records.

3. EXISTING AND PROPOSED SYSTEMS

3.1 Existing Manual System

Faculty members prepare questions and submit hard copies. A scrutiny committee manually counts questions and marks per unit using pencil and paper, cross-verifies syllabus coverage, and manually writes remarks on physical scrutiny proformas.

3.2 Disadvantages of the Existing System

  • Prone to arithmetic errors during mark summations.
  • Subjective tagging of Bloom’s cognitive levels without semantic verification.
  • No mechanism to detect question repetition from past tests or within the same paper.
  • Physical paperwork is easily misplaced, complicating NBA audit compliance.

3.3 Proposed Automated System

A structured, menu-driven C program that implements 5 distinct modules, executes deterministic algorithmic checks, evaluates Course Outcome coverage, computes difficulty ratings, and generates timestamped audit certificates.

4. REQUIREMENTS AND FEASIBILITY STUDY

4.1 Functional Requirements

  • FR1: Blueprint rule entry, modification, listing, and file persistence.
  • FR2: Question inventory entry with question statement, unit, CO, topic, Bloom level, and marks.
  • FR3: Categorization and aggregation of marks per Unit (1–5), CO (1–5), and Bloom's level (L1–L6).
  • FR4: Automated difference calculation (Δ = Actual - Expected) and Compliance Percentage generation.
  • FR5: Calculation of Weighted Difficulty Index.
  • FR6: AI Action Verb checking and Jaccard Question Similarity scanning.
  • FR7: File persistence and export to text and CSV.

4.2 Non-Functional Requirements

Standard C99 portability across all operating systems, execution latency under 100 milliseconds, memory safety, and intuitive ANSI color highlights.

5. SYSTEM ARCHITECTURE AND DESIGN

The application follows a modular architecture separating data representation (models.h), business logic (checker.c, analysis.c), AI processing (ai_helper.c), input/output (blueprint.c, question_paper.c), and reporting (report.c).

6. FIVE MODULES: DESIGN, ALGORITHMS, AND PSEUDOCODE

Module 1: Blueprint Management

Responsible for defining and storing the reference examination blueprint standards. 

ALGORITHM Module1_AddRule:
1. Input Unit, CO Number, Topic Name, Cognitive Level (1 to 6), Expected Questions, and Marks.
2. If rule_count < MAX_RULES:
     Store parameters into rules[rule_count].
     Increment rule_count.
     Recalculate total_expected_marks = SUM(rules[i].expected_marks).
3. Display confirmation.

Module 2: Question Paper Management

Captures, inventories, and modifies the questions of the submitted examination paper. 

ALGORITHM Module2_AddQuestion:
1. Input Question No, Statement, Unit, CO, Topic, Cognitive Level, and Marks.
2. Call ai_verify_question_alignment(statement, cognitive_level).
3. Append record into questions[question_count].
4. Recalculate total_marks = SUM(questions[i].marks).

Module 3: Data Organization and Analysis

Organizes and aggregates raw questions into frequency distributions across units, COs, and Bloom levels. 

ALGORITHM Module3_OrganizeData:
1. Clear unit_stats[1..5], co_stats[1..5], cog_stats[1..6].
2. For each rule in blueprint:
     expected_marks[rule.unit] += rule.expected_marks.
     expected_marks[rule.co] += rule.expected_marks.
     expected_marks[rule.cog] += rule.expected_marks.
3. For each question in question paper:
     actual_marks[question.unit] += question.marks.
     actual_marks[question.co] += question.marks.
     actual_marks[question.cog] += question.marks.
     weighted_sum += question.cognitive_level * question.marks.
4. Calculate Difficulty Index = weighted_sum / total_marks.
5. Compute differences: marks_diff = actual_marks - expected_marks.

Module 4: Blueprint Checking and Comparison Engine

The core audit engine that identifies discrepancies and computes the normalized Compliance Percentage Score. 

ALGORITHM Module4_CheckCompliance:
1. Compute total_error = SUM(|unit_marks_diff|) + SUM(|co_marks_diff|) + SUM(|cog_marks_diff|).
2. Max_Penalty = 2 * total_expected_marks.
3. Compliance_Score = MAX(0.0, 100.0 - ((total_error / Max_Penalty) * 100.0)).
4. If Compliance_Score == 100.0 THEN Verdict = "100% COMPLIANT - APPROVED FOR EXAMINATION".
   Else If Compliance_Score >= 80.0 THEN Verdict = "PARTIALLY COMPLIANT - MINOR CORRECTIONS REQUIRED".
   Else Verdict = "NON-COMPLIANT - REJECTED (REVISION REQUIRED)".

Module 5: Report Generation and File Management

Formats tables and writes structured audit certificates to audit_report.txt and audit_report.csv.

7. DATA DESIGN AND FILE HANDLING

All records are defined in models.h using fixed-size C structures. File persistence utilizes standard C stream I/O (fopen, fprintf, fscanf, fgets, fclose).

8. USER INTERFACE AND CONSOLE DESIGN

The interface uses a numbered menu loop with ANSI escape sequences (\033[1;32m Green, \033[1;33m Yellow, \033[1;31m Red, \033[1;36m Cyan) to provide high visual clarity during presentations.

9. CORE IMPLEMENTATION & AI MODULES

9.1 Bloom's Action Verb Natural Language Classifier

The classifier scans question statements for key action verbs:

  • L1 (Remember): define, state, list, name, recall, identify, what is, mention
  • L2 (Understand): explain, describe, discuss, outline, summarize, clarify, illustrate
  • L3 (Apply): calculate, compute, solve, implement, demonstrate, execute, apply
  • L4 (Analyze): analyze, differentiate, distinguish, compare, contrast, examine
  • L5 (Evaluate): evaluate, justify, critique, verify, assess, defend, rate
  • L6 (Create): design, formulate, construct, develop, compose, invent, propose

9.2 Jaccard Question Similarity Detector

Detects potential duplicate questions across the paper using token-based Jaccard similarity:

J(QA, QB) = |QA ∩ QB| / |QA ∪ QB|

If similarity ≥ 35%, the system issues a redundancy alert.

9.3 Weighted Paper Difficulty Index

Difficulty Index = ∑ (Cognitive Leveli × Marksi) / Total Marks

  • < 2.20: Easy (Heavy Lower-Order Thinking)
  • 2.20 – 3.80: Well-Balanced (Ideal for Autonomous Examinations)
  • > 3.80: Highly Challenging (Excessive Higher-Order Thinking)

10. INTEGRATION AND DATA FLOW

The menu-driven system coordinates all modules: data entered into Module 1 and 2 flows into Module 3 for aggregation, passes through Module 4 for discrepancy audits, and is emitted by Module 5 as terminal output and persistent disk files.

12. SECURITY, RELIABILITY, LIMITATIONS, AND FUTURE ENHANCEMENTS

12.1 Reliability & Security

The application enforces strict array bound limits, validates numeric menu options against unexpected characters, uses bounded string copies (strncpy), and handles missing files gracefully.

12.2 Limitations

Currently designed as a console application with question statements capped at 256 characters. Storage is file-based (TXT/CSV) rather than an enterprise database.

12.3 Future Enhancements

Future versions can include a web GUI, automated question extraction from scanned DOCX/PDF files via OCR, and integration with large language model APIs for deep semantic Bloom classification.

13. CONCLUSION

The Examination Question Paper Blueprint Checker successfully automates the scrutiny and validation of examination question papers according to autonomous college regulations, Outcome-Based Education (OBE), and Bloom’s Revised Taxonomy. Developed in modular C, the system enforces mathematical precision in marks allocation, Course Outcome coverage (CO1–CO5), and cognitive level distributions while eliminating human calculation oversights. Generating persistent audit documentation in formatted text and Microsoft Excel formats provides an objective and verifiable audit trail that strengthens academic rigor and supports institutional accreditation.
